# V03 — 실연결 검증 보고서와 화면 상태 검토

검토일: 2026-11-12. 대상은 `scripts/check_api.py`, `app/config.py`, `/api/health`, 실거래 화면의 연결 상태 표현이다. 이 검토자는 사용자 인증키·실제 설정 파일·업로드 원본을 열지 않았으며 외부 요청을 실행하지 않았다. 아래 테스트는 모두 가짜 키와 오프라인 대체 응답을 사용한다. 실제 인증 결과는 별도 실호출 담당자가 만든 최신 `reports/api_verification_report.json`을 기준으로 판단한다.

## 발견한 문제와 수정

검증 보고서가 시각·결과·건수는 저장했지만 조회 지역·계약월·페이지 조건은 저장하지 않았다. 예를 들어 기본값이 아닌 `11110 / 202501`로 성공해도 보고서만으로는 어느 조회의 성공인지 재현할 수 없었다.

`scripts/check_api.py`의 보고서 스키마를 `1.1`로 올리고 다음을 추가했다.

| 필드 | 의미와 제한 |
|---|---|
| `query.kind` | 요청한 `trade`, `rent`, `both` |
| `query.lawd_cd` | 검사를 통과한 ASCII 숫자 5자리 지역 코드 |
| `query.deal_ymd` | 검사를 통과한 유효한 `YYYYMM` 계약월 |
| `query.page_no` / `num_of_rows` | 실제 검사 요청의 첫 페이지 / 최대 5건 |
| `provenance.requested_mode` | `live`: 실제 국토부 조회를 요청하는 실행 경로 |
| `provenance.provider` | `molit` |
| `provenance.synthetic_fallback` | `false`: 실조회 실패를 가상 자료로 대체하지 않음 |
| `provenance.verification_scope` | `single_page_authenticated_response`: 한 페이지 인증 응답 확인 범위 |

하나라도 잘못된 조회 인수가 있으면 `query` 전체를 `null`로 쓴다. 잘못된 인수에 인증키나 다른 비밀값이 들어 있어도 보고서·콘솔로 복사하지 않는다. provenance는 요청 경로와 검증 범위이며, `NOT_RUN` 항목까지 실제 네트워크 호출이나 인증이 완료되었다는 뜻은 아니다. 원본 응답, 거래 항목, 단지명, 인증키, 제공기관 원문 메시지는 계속 기록하지 않는다.

## 상태 해석 확인

| 관찰 대상 | 확인한 동작 | 해석 |
|---|---|---|
| 키 설정과 `/api/health` | 키 존재 여부와 별개로 `verified=false` | 설정만으로 실제 연결 성공을 주장하지 않음 |
| 화면 연결 배지 | `키 설정됨`과 `실제 조회 별도 검증` 표시 | 키가 있다는 사실만 안내함 |
| 화면 실제 조회 | `source=molit`, `synthetic=false` 응답만 표시 | 가상 응답을 실거래로 표시하지 않음 |
| 두 서비스 모두 정상 | `VERIFIED`, `both_apis_verified=true` | 이번 실행에서 두 서비스의 한 페이지 응답 확인 |
| 한 서비스만 선택 | 다른 서비스는 `NOT_REQUESTED` | 한 API 성공으로 두 API가 검증되었다고 표시하지 않음 |
| 일부 행 변환 실패 | `PARTIAL`, 제외 건수와 경고 | 읽지 못한 행이 있으면 전체 정상으로 표시하지 않음 |
| 정상 0건 응답 | 정상 응답으로 기록하며 별도 경고 | 개별 거래 필드·금액 단위·해제값 대조 완료를 뜻하지 않음 |
| 오류 응답 | 정해진 안전 코드와 문구만 사용 | 원문 응답이나 인증키를 공유 보고서로 복사하지 않음 |

`checked_at`, `started_at`, `finished_at`은 보고서 작성 프로그램의 UTC 시각이다. `checked_at`은 `NOT_RUN`이나 `NOT_REQUESTED`에도 있으므로 네트워크 호출의 증거로 단독 해석하면 안 된다. `FAILED`에는 클라이언트 사전 검사 실패도 포함될 수 있으므로 서비스별 `code`도 읽어야 한다. 현재 보고서는 키 식별자나 키 지문을 저장하지 않으며, 키 변경 이후에도 예전 성공이 유지된다고 보장하지 않는다.

앱은 저장된 보고서를 자동으로 읽어 `/api/health`의 `verified`를 바꾸지 않는다. 따라서 실제 검사 성공 후에도 health의 값은 자동 갱신되지 않는다. 키가 존재한다는 이유나 오래된 보고서만으로 health를 `true`로 바꾸지 않는 현재 동작은 유지했다. Zoro 실행·현재 매물·현장 상태·외부 예약의 검증 범위도 아니다.

## 인증 오류가 빈 성공으로 바뀌는 경로

별도 클라이언트 검토자에게 다음 오류 경로를 전달했다. 명시적 인증 오류 코드와 `NO_DATA`/`NODATA_ERROR` 문구가 동시에 있을 때, 기존 파서는 빈 성공을 먼저 반환하여 검사 보고서가 잘못 `VERIFIED`가 될 수 있었다. 클라이언트 검토자는 `app/molit.py`에서 명시적 오류 코드의 우선순위를 수정하고 오프라인 회귀 테스트를 추가했다. 이 보고서 작업에서는 해당 파일을 중복 수정하지 않았다.

## 검증 결과와 실호출 기록의 경계

실행 명령:

```text
.venv/bin/python -m pytest -q tests/test_report_v03.py tests/test_key_setup.py tests/test_config.py
```

결과: **71 passed**, 의존성의 pytest 이름 변경 예정 경고 1건. 새 보고서 테스트는 기본값이 아닌 조회 조건 보존, 보고서 조건과 실제 전달 인수의 일치, 세 가지 인수 위치의 잘못된 값 비노출, 키가 없어 실행되지 않은 조회의 상태 보존을 검사한다. 인증 오류와 `NO_DATA` 문구가 섞인 두 XML 형식에 대해서도 실제 HTTP 클라이언트·파서·보고서 경로를 오프라인 전송기로 연결하여 `FAILED / MOLIT_AUTH_ERROR`가 되고 `VERIFIED`가 되지 않는 것을 확인했다. 이 테스트 통과는 실제 국토부 연결 성공이 아니다.

검토 시작 시 확인한 기존 보고서는 `2026-11-12T08:57:41.410808+00:00` 종료, `NOT_RUN`, 두 API 모두 `MOLIT_KEY_MISSING`이었다. 이후 실호출 담당자가 보고서를 교체하면 그 최신 파일의 시각·조건·서비스별 결과를 사용해야 한다. 기존 파일의 내용을 이번 검토의 실호출 결과로 재사용하지 않는다.
