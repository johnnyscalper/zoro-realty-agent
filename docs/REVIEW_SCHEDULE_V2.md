# v0.2 일정 도구 독립 검토

검토일: 2026-11-12. 대상: `CONTRACT_STAGE5.md`, `app/scheduling.py`, `app/tools.py`, 일정 HTTP 경계, 관련 단위·통합 검사 및 실행실의 일정 표시 코드. 모든 업체 가능 시간은 명시적인 가상 입력이다. 실제 업체 조회·연락·예약 또는 Zoro 실행은 하지 않았다.

## 결론

현재 세 개 일정과 여섯 개 업체 시간으로 구성된 시연 경로에서, 잘못된 대안을 적용하거나 사용자 선택 없이 청소·이사를 옮기는 백엔드 결함은 발견하지 못했다. 기존 일정·도구 API 검사 131개를 깨끗한 Python 환경에서 다시 실행하여 모두 통과했다. 아래 두 항목은 별도로 전달했다. 첫 항목은 검토 중 UI 담당자가 수정했고, 두 번째는 더 큰 일정으로 확장할 때의 탐색 비용 문제로 남아 있다.

## 발견 사항

### SCHED-R1 — 무효화된 대안을 ‘가능한 대안 없음’으로 표시할 수 있음

우선순위: P2, 화면 안내의 정확성. **검토 중 수정됨.** 최초 `static/app.js`에서 소스 흐름으로 확인했으며 UI 담당자에게 전달했다.

재현 순서:

1. 실행실 세션을 만들고 `일정 대안 만들기`를 눌러 실제로 대안이 나오는 것을 확인한다.
2. `후보 다시 검색`을 누른다. 서버는 새 버전을 저장하고 이전 `schedule_proposals`를 비운다.
3. `workbench.proposalsChecked`는 `true`인 채 남으므로 `renderSchedule()`이 “등록된 업체 가능 시간으로 충돌 없는 대안을 만들 수 없습니다”라고 표시한다.

이때 시간·업체 슬롯은 바뀌지 않았으며 다시 계산하면 대안이 나온다. 이전 계산 결과가 무효화된 상태를 불가능 판정으로 설명하는 것이다. 확인 요청·확인 결과 저장에서도 같은 경로가 있다. 매물 상태 변경 핸들러는 플래그를 나중에 지우지만, `mutate()`가 먼저 화면을 다시 그리므로 표시가 이미 잘못된 채 남을 수 있다.

반영된 수정: `mutate()`가 `acceptSession()` 호출 전에 `proposalsChecked = path === "/schedule/proposals"`를 설정한다. 대안 계산 이외의 성공적인 변경은 잘못된 불가능 안내를 즉시 해제한다. 명시적인 세션 새로고침은 대안 목록이 비어 있을 때 다시 계산하라는 중립적인 안내를 보여 준다. 변경된 소스는 다시 읽어 확인했으며 이 독립 검토에서 브라우저로 수정 후 동작을 실행한 것은 아니다. 백엔드의 버전·저장된 대안 검증은 정상 동작하므로 이 문제로 오래된 대안이 적용되지는 않는다.

### SCHED-R2 — 입력 개수 제한만으로 대안 탐색 비용을 제한하지 못함

우선순위: P3, 확장 전 보완. 현재 공개 API는 일정 목록·슬롯을 받지 않고 고정 시연 자료를 사용하므로 현재 사용자 경로의 차단 결함으로 분류하지 않는다.

`validate_schedule()`은 최대 100개 일정과 1,000개 슬롯을 허용한다. `propose_schedules()`의 깊이 우선 탐색은 뒤쪽 일정이 불가능한 경우에도 앞쪽 슬롯 조합을 전부 순회한다. 대안 개수 제한 5개는 성공 결과에만 적용되어 실패 탐색량을 제한하지 않는다.

오프라인 확인: 서로 독립인 청소 일정 N개가 각각 두 개의 한 시간 창에 들어갈 수 있고, 마지막 이사 일정에 대응하는 슬롯이 없는 유효한 구조를 입력했다. 결과는 모두 `[]`지만 측정 시간은 다음과 같이 증가했다. 측정은 해당 환경의 단일 실행이며 성능 보장이 아니다.

| 청소 일정 수 N | 측정 시간 |
| --- | ---: |
| 8 | 0.0037초 |
| 10 | 0.0137초 |
| 12 | 0.0548초 |
| 14 | 0.2088초 |

각 청소 일정이 두 가지 분기를 만들므로 이 구성은 `2^N`에 비례하는 탐색을 수행한다. 실제로 더 큰 입력을 장시간 실행하지는 않았다. 도구의 대안 계산은 SQLite 쓰기 트랜잭션 안에서 실행되므로, 향후 이런 입력을 허용하면 다른 세션의 쓰기도 지연될 수 있다.

권장 수정: 서비스별로 소요 시간을 수용하는 슬롯이 전혀 없는 경우 먼저 종료한다. 더 일반적인 조합 폭증에는 의존성별 가지치기나 탐색량 제한을 추가하고, 탐색을 중단했다면 ‘실행 가능한 대안 없음’과 구분되는 안전한 오류를 반환한다. 임의로 검색을 잘라 놓고 빈 배열을 반환해서는 안 된다.

## 확인한 주요 불변식

- 모든 시각에 명시적 시간대가 필요하며 비교는 절대 시각으로 수행된다. 종료와 다음 시작이 같은 경계는 허용된다.
- 입주 종료가 실제 접근 가능 시각이다. 입주 변경은 그 일정의 원래 길이만 보존하며 후속 일정을 자동 변경하지 않는다.
- 청소·이사는 하나의 제공된 가능 시간 안에 전체 소요 시간이 들어가야 한다. 서로 떨어진 창을 합쳐서 가용 시간을 만들지 않는다.
- 선행 관계는 존재하는 일정만 참조하고 순환을 거부한다. 제안은 사건 ID·종류·상태·소요 시간·선행 관계를 보존하며 입주 시각을 고정한다.
- 제안은 슬롯별로 선행 일정 종료 이후의 가장 이른 배치를 찾는다. 현재와 동일한 안과 중복 안을 제외하고 최대 다섯 개를 결정적으로 반환한다. 모든 가능한 시작 시각을 열거한다는 의미는 아니다.
- 제안 계산만으로 현재 일정은 바뀌지 않는다. 다음 날로 넘어가는 안도 사용자가 저장된 대안 ID를 명시적으로 선택해야 반영된다.
- 서버는 현재 세션에 저장된 대안만 조회하고 기준 버전과 현재 버전을 검사한다. 적용 시 현재 슬롯·선행 관계·기간을 다시 검사하고 이후 대안을 지운다.
- UI는 쓰기 충돌 시 새로고침을 안내하며 자동 재시도하지 않는다. 제안 화면과 감사 기록은 외부 예약을 수행하지 않았음을 명시한다.

## 실제 수행한 검증

명령: `../zoro-clean-check/bin/python -m pytest -q tests/test_scheduling.py tests/test_tools_api.py`.

결과: **131 passed**, FastAPI/Starlette 테스트 클라이언트의 기존 사용 중단 경고 1개. 네트워크 API는 호출하지 않았다.

추가로 임시 SQLite와 HTTP 테스트 클라이언트에서 다음을 직접 확인했다.

- 검색·조건 변경·확인 요청·매물 상태 변경·입주 변경의 다섯 경로 모두 이전 대안을 비우고, 이전 ID로 적용하면 409를 반환한다.
- 적용 요청에 대안 ID 외에 `events`를 삽입하면 422로 거부되며 저장 상태가 바뀌지 않는다.
- 정상 적용 후 같은 대안을 다시 사용하면 409로 거부되며 저장 상태가 바뀌지 않는다.

이 검토는 기존 검사와 실제 오류 재현을 중심으로 수행했다. 구현을 그대로 되풀이하는 검사나 장시간 멈출 수 있는 스트레스 검사를 새 기본 테스트 파일에 추가하지 않았다. 프로덕션 파일은 수정하지 않았다.

## 범위의 한계

슬롯은 제공된 가상 가능 시간 창이다. 외부 예약 재고, 업체별 인원·차량 용량, 준비·이동 시간, 실시간 슬롯 만료 및 사용자의 실제 입주 기한과 서비스 완료 시각의 관계까지 검증하는 모델은 아니다. 현재 계약이 요구하는 선행 관계·소요 시간·제공 슬롯의 범위에서만 실행 가능하다고 해석해야 한다.
