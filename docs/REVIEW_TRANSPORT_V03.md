# V03 — 전송 설정과 실패 근거 검토

검토일: 2026-11-12. 대상은 `app/molit.py`, `scripts/check_api.py`, `/api/transactions`의 예외 처리와 설치된 HTTPX 0.28.1의 전송 설정이다. 이 검토는 사용자 인증키·실제 `.env`·업로드 파일을 읽지 않았고 네트워크 요청을 보내지 않았다. 테스트는 가짜 키, 임시 보고서와 오프라인 전송기만 사용했다. 운영 코드는 변경하지 않았다.

결과: **기본 직접 연결 정책은 유지할 수 있다. 클라우드의 직접 연결 실패를 인증키 실패나 국토부 장애로 단정할 수 없다.** 새 테스트 10건을 포함한 관련 테스트 111건이 통과했다. 실제 Windows 실행, 실제 TLS 연결 및 인증 응답은 이 검토의 증거가 아니다.

## 기본 연결 정책과 환경 차이

`fetch_transactions()`가 직접 만드는 클라이언트는 `httpx.AsyncClient(follow_redirects=False, trust_env=False)`다. 설치된 HTTPX 소스에서 다음 동작을 확인했다.

| 설정 | 현재 동작 | 의미 |
|---|---|---|
| HTTPS와 인증서 검증 | HTTPS 주소를 사용하며 기본 `verify=True`를 유지한다. HTTPX가 certifi 인증서 묶음으로 SSL 컨텍스트를 만든다. | 인증서·호스트 검증을 끄지 않는다. 오프라인 테스트가 실제 인증서 교환을 검증했다는 뜻은 아니다. |
| 환경 프록시 | 기본 클라이언트는 `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`와 관련 우회 설정을 상속하지 않는다. | 직접 인터넷 연결이 가능한 사용자 PC를 위한 정책이다. 프록시 경유가 필수인 실행 환경에서는 그대로 성공한다고 보장할 수 없다. |
| 환경 CA | 기본 클라이언트는 `SSL_CERT_FILE`, `SSL_CERT_DIR`를 상속하지 않는다. | 조직 또는 실행 환경이 별도 CA를 요구하면 해당 환경 설정만으로 앱에 적용되지 않는다. |
| 리다이렉트 | 클라이언트와 요청 모두 자동 이동을 끄고 3xx를 오류로 반환한다. | 인증키가 다른 주소로 자동 전달되지 않는다. |
| 주입한 클라이언트 | 호출자가 만든 `client`를 그대로 사용하며 함수가 닫지 않는다. | 주입한 클라이언트의 프록시·TLS 정책까지 기본 클라이언트와 같다고 주장할 수 없다. 앱과 검사 CLI는 현재 이 경로로 별도 프록시를 구성하지 않는다. |

표준 Windows 직접 연결 경로를 클라우드에 맞추기 위해 `trust_env=True`로 일괄 변경할 근거는 없다. 그 변경은 환경 프록시와 CA를 신뢰하도록 정책을 바꾸며, SOCKS 프록시를 읽으면 `socksio` 추가 의존성이 필요할 수 있다. 현재 `requirements.txt`의 `httpx==0.28.1`은 SOCKS 추가 기능을 선언하지 않는다. 진단용 환경에 일시 설치한 패키지가 배포 패키지의 지원 범위를 바꾸지는 않는다.

프록시 지원을 제품 기능으로 추가한다면 명시적인 설정·의존성·오류 분류·비밀값 비노출 검증이 함께 필요하다. 현 범위에서는 기본 직접 연결, 인증서 검증과 리다이렉트 차단을 유지한다. TLS 검증 해제나 네트워크 제한 우회는 수정안이 아니다.

## 오류 코드가 증명하는 범위

오류 코드는 사용자에게 보여줄 안전한 분류다. 네트워크 단계의 전체 기록이나 오류 발생 주체의 신원 증명은 아니다.

| 관찰 | 현재 공개 결과 | 해석할 수 있는 범위 |
|---|---|---|
| 클라이언트 생성 실패 | 웹 API는 `UPSTREAM_FAILURE`; 검사기는 `FAILED` | 요청 시작 전에 실패할 수 있다. 현재 함수 내부의 `MolitError` 변환 대상이 아니며, 상위 호출자가 원문 예외를 숨긴다. |
| DNS·연결·프록시 계열 `httpx.RequestError` | `MOLIT_CONNECTION_ERROR` | 연결 계열 실패다. 실제 DNS `ConnectError`를 별도로 관찰했다면 그 시도는 제공기관 응답 이전에 실패했다고 설명할 수 있다. 코드만으로 DNS 문제를 확정할 수는 없다. |
| HTTP 200 헤더 이후 본문 읽기 `ReadError` | 역시 `MOLIT_CONNECTION_ERROR` | HTTP 응답을 받은 뒤에도 같은 코드가 생긴다. 코드만으로 “어떤 응답도 받지 않았다”고 쓰면 부정확하다. |
| HTTPX 시간 초과, HTTP 408/504 또는 제공기관 시간 초과 코드 | `MOLIT_TIMEOUT` | 연결·읽기·풀 대기 또는 상위 시간 초과를 같은 공개 코드로 표시한다. 코드만으로 실패 단계를 구분하지 않는다. |
| HTTP 5xx | `MOLIT_UPSTREAM_ERROR` | 해당 조회 경로에서 HTTP 오류 응답을 받았다. 프록시나 게이트웨이가 생성한 응답일 수도 있으므로 국토부 애플리케이션이 직접 생성했다고 단정하지 않는다. |
| HTTP 401/403 | `MOLIT_AUTH_ERROR` | 접근 거절 응답이다. 중간 계층의 응답일 가능성까지 배제하거나 키 자체가 잘못됐다고 확정하지 않는다. |
| HTTP 200 및 성공 XML 파싱 | 페이지 결과 또는 정상 0건 | 이 조회 응답의 파싱 결과다. 인증된 실제 호출인지, 가짜 전송기를 썼는지는 실행 근거와 함께 판단한다. |

`check_api.py`는 실패 시 `both_apis_verified=false`를 유지한다. 생성 시각과 `provenance.requested_mode=live`는 실패한 실행도 기록하므로 성공적인 인증이나 제공기관 도달의 독립 증거가 아니다. 검사 보고서와 화면에서 가상 거래로 실패를 대체하지 않는 원칙도 유지된다.

## 클라이언트 생성 위치의 진단 한계

현재 `active = client or httpx.AsyncClient(...)`는 `try` 앞에 있다. 따라서 인증서 파일, SSL 컨텍스트, 프록시 설정 또는 선택 의존성 때문에 생성자가 실패하면 `fetch_transactions()` 내부의 안전한 `MolitError` 분류를 거치지 않는다. 기본 `trust_env=False`에서는 환경 프록시와 환경 CA 때문에 발생하는 일부 원인이 적용되지 않지만, 생성 실패 자체가 불가능한 것은 아니다.

웹 API와 검사 CLI에는 이미 원문 예외를 반환·출력하지 않는 일반 예외 처리가 있다. 따라서 현재 사용자 경로에서는 해당 실패를 인증 성공으로 표시하거나 원문 예외를 노출하지 않는다. 다만 세부 원인은 일반 실패로 합쳐진다. 향후 프록시 또는 사용자 지정 CA를 지원할 때는 생성 단계에서 알려진 구성 오류를 고정 문구로 분류하고, 오류 원문·프록시 인증정보·경로·키를 보고서에 복사하지 않도록 함께 수정해야 한다. 생성자를 단순히 기존 `try` 안으로 옮기는 것만으로는 `OSError`, `ValueError`, `ImportError`가 기존 `httpx.RequestError` 처리에 포함되지 않는다.

## 통합 담당자가 전달한 클라우드 진단의 해석

이 검토 시점에 통합 담당자가 전달한 관찰은 다음과 같다. 이 검토자가 해당 요청을 재실행하거나 실제 비밀값을 확인한 것은 아니다. 최종 실호출 결과는 통합 담당자가 남긴 최신 시각·조건·서비스별 기록을 따른다.

1. 기본 `trust_env=False` 경로는 DNS 관련 `ConnectError`로 실패했다. 이 관찰은 해당 시도에서 제공기관 응답을 받기 전에 실패했다는 설명을 뒷받침한다. 키 유효성·활용승인·거래 필드 변환은 판단할 수 없다.
2. 환경 프록시와 CA를 사용하는 별도 비인증 진단 경로에서는 공식 주소 조회에 HTTP 503이 관찰됐다. 이 결과는 조회 경로에서 HTTP 응답을 받았다는 근거이며, 인증된 국토부 성공 응답이나 국토부 자체 장애의 확정 근거가 아니다.
3. 두 경로는 설정과 인증 여부가 다르다. 두 번째 관찰을 첫 번째 앱 요청의 결과로 대체하거나 “실거래 연결 검증 완료”로 합쳐 기록하면 안 된다.

## 추가 테스트와 실행 결과

새 파일: `tests/test_transport_v03.py`. 기존의 주입된 클라이언트 중심 테스트가 우회했던 기본 클라이언트 생성 경로를 대상으로 했다. 테스트 안에서 프록시·CA 환경값을 가짜 값으로 교체하며 실제 환경값을 출력하지 않는다. `Settings.from_env`와 실제 요청 전송을 차단해 로컬 설정 읽기와 외부 통신을 방지했다.

| 새 검사 | 건수 | 검증한 성질 |
|---|---:|---|
| 기본 클라이언트 생성 | 1 | 환경 프록시·CA 무시, HTTPS·기본 인증서 검증·리다이렉트 차단 설정, 정상 종료 시 클라이언트 닫힘 |
| 연결·프록시·연결 시간 초과·읽기 시간 초과 | 4 | 안전한 코드·HTTP 상태·재시도 표시, 한 번만 요청, 비밀값 비노출, 실패 시 클라이언트 닫힘 |
| 200 응답 뒤 본문 읽기 실패 | 1 | 실패가 성공으로 바뀌지 않음; 연결 코드만으로 응답 이전 실패를 추론할 수 없음을 확인 |
| 주입한 클라이언트 소유권 | 1 | 호출자가 닫기 전 함수가 임의로 닫지 않음 |
| 생성자의 파일·값·의존성 오류 | 3 | 검사 결과는 실패·미검증이며 건수가 채워지지 않음; 보고서·콘솔에 예외 속 가짜 비밀값이 나오지 않음 |

실행 명령:

```text
../zoro-clean-check/bin/python -m pytest -q tests/test_transport_v03.py tests/test_molit.py tests/test_client_v03.py tests/test_report_v03.py tests/test_secrets_v03.py
```

결과: **111 passed in 0.40s**. 이는 전송 설정과 오류 경계의 오프라인 회귀 검증이다. 네트워크 도달, 실제 TLS 성공, 사용자 키·승인 유효성, Windows 호스트 실행을 대신하지 않는다.
