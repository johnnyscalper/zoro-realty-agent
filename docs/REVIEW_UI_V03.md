# 실거래 화면 독립 검토 — v0.3

검토일: 2026-11-12. 범위: `static/app.js`, `static/index.html`, `static/styles.css`와 국토부 응답 계약을 연결해 조회 화면의 상태 전환을 검토했다. 사용자 인증키·`.env`·업로드 자료를 읽지 않았고, 서버·브라우저를 실행하지 않았다. 실제 API 호출이나 실제 브라우저 표시 검증을 완료했다는 뜻이 아니다.

## 발견 사항

### UI-01 — 편집 중인 조회 조건과 이전 결과가 함께 보임

- 위치: `static/app.js`의 거래 폼 이벤트 등록(검토 시 532행), 결과 메타 표시(404~412행).
- 재현: `11680` 조회를 완료한 뒤 시군구 코드 입력란에 포커스를 둔 채 `11110`으로 바꾼다. 텍스트 편집의 `input` 이벤트는 처리하지 않고 `change` 때만 결과를 지우므로, 포커스를 옮기기 전까지 기존 `11680` 표와 다음 페이지 버튼이 남는다. 진행 중인 이전 요청도 이 시점에는 취소되지 않는다.
- 오프라인 재현 결과: `current_form_district=11110`, `saved_result_district=11680`, `table_still_visible=true`. 이후 `change`를 보내면 정상적으로 초기화된다.
- 영향: 결과 메타에 실제 요청 지역·연월을 따로 표시하지 않아, 새 입력 조건의 결과로 오해할 여지가 있다. 모드·거래 종류 선택을 확정했을 때의 취소 처리는 정상이다.
- 권고: 조회 조건의 `input` 시점에 이전 결과와 진행 중인 요청을 취소하거나, 결과에 제출 당시 조회 조건을 명확하게 고정 표시한다.
- 수정: 통합 담당자의 파일 소유권 확인 후 거래 폼에 `input` 이벤트 처리를 추가했다. 입력 즉시 기존 결과·저장된 조회·페이지 버튼을 지우고 진행 중인 요청을 취소한다. 기존 `change` 처리도 유지했다.
- 확인: 포커스를 옮기지 않고 입력만 바꿨을 때 완료 결과를 지우는 경우와 진행 중인 요청을 취소하고 늦은 응답을 무시하는 경우를 각각 회귀 검사로 추가해 통과했다. 실제 브라우저 이벤트 확인은 통합 담당자가 수행한다.

### UI-02 — 허용된 큰 금액이 JSON → JavaScript 경계에서 반올림됨

- 위치: `app/molit.py`의 `_money()`(검토 시 132~138행), `static/app.js`의 `getJSON()`·`won()`(147~158, 197행).
- 서버는 최대 `10**17`원의 정수를 허용한다. 브라우저는 `response.json()`의 JavaScript Number와 `Number(value)`로 금액을 처리하므로, `2**53 - 1`을 넘는 일부 정수 원화는 정확하지 않다.
- 재현: 합성 XML의 `dealAmount`를 `900719925474.0993`만원으로 바꾸고 실제 파서를 사용했다. 파서는 정확히 `9007199254740993`원을 반환했지만, 같은 JSON의 Node `JSON.parse()` 결과는 `9007199254740992`원이었다.
- 영향: 통상적인 아파트 거래보다 매우 큰 금액에 해당하므로 실제 발생 가능성은 낮지만, 현재 허용 입력 범위 안에서 원 단위 정확성 계약이 깨진다. 보증금·월세에도 같은 경계가 적용된다.
- 권고: 외부 금액을 JavaScript 안전 정수 범위로 제한해 잘못된 행으로 세거나, 정수 문자열을 전송하고 문자열/BigInt로 끝까지 표시한다.
- 상태: 발견 후 통합 담당자에게 즉시 전달. 별도 금액 담당자가 서버 안전 정수 범위 제한을 수정 중이며, 이 검토자는 금액 코드를 수정하지 않았다.

## 확인한 정상 동작

| 범위 | 확인 결과 |
| --- | --- |
| 키 설정과 검증 구분 | 두 키 설정 여부를 개별 확인하며, 화면은 `키 설정됨 / 실제 조회 별도 검증`으로 표시한다. Zoro 주소 설정도 실제 연결·판단 미검증으로 남는다. |
| API 종류별 요청 제한 | 전월세 키가 없으면 전월세 실제 조회만 막고, 매매 키가 있으면 매매 실제 조회를 허용한다. 가상 조회는 키 없이 가능하다. |
| 상태 확인 실패 | 건강 상태 조회 실패 후 실제 조회 버튼을 다시 막고 오류를 표시한다. |
| 모드 전환·요청 취소 | `input` 또는 `change` 후 결과를 지우고 AbortController를 취소한다. 취소를 무시하고 늦게 완료되는 응답도 컨트롤러 식별 비교로 무시한다. |
| 겹친 요청 | 이전 요청의 catch/finally가 새 요청의 로딩 상태·결과를 덮어쓰지 않는다. |
| 가상/실제 출처 | 실제 조회에서 합성 응답이 오면 표시를 거부한다. 실제 요청 실패 후 가상 자료를 불러오지 않는다. |
| 0건·전체 정규화 실패 | 실제 0건과 전부 제외된 자료를 서로 다른 안내로 표시한다. 현재 매물이 없다는 주장으로 바꾸지 않는다. |
| 부분 결과 | 유효한 행, 제외 건수 경고, 공급자 전체 건수를 함께 보존한다. |
| 빈 후속 페이지 | 전체 자료가 있음을 표시하고 이전 페이지 이동을 유지한다. 빈 첫 페이지라도 `has_next=true`이면 다음 페이지를 유지한다. |
| 페이지 이동 | 제출한 조회 조건과 20행 크기를 유지하고 page_no만 바꾼다. 요청 중 두 페이지 버튼을 막고 완료 후 가능한 방향만 허용한다. |
| 금액·거래 종류 | 매매는 `price_krw`, 전월세는 `deposit_krw`와 `monthly_rent_krw`를 표시한다. 안전 정수 범위의 1원 단위까지 보존한다. 0원 월세를 전세로 표시한다. |
| 해제 상태 | 매매 해제 신고와 날짜를 보여준다. 전월세의 `cancelled=false`를 계약 유효 보장으로 설명하지 않고 해제 여부 확인 불가를 표시한다. |
| 좁은 표 | CSS에 표의 가로 스크롤과 focus 가능한 래퍼가 있으며, 별도의 표 설명이 있다. 실제 좁은 화면 크기·터치 동작은 이 검토에서 실행하지 않았다. |

## 추가 관찰

- 후속 페이지 조회가 실패하면 직전 페이지 결과와 페이지 버튼을 지운다. 주 조회 버튼으로 재시도하면 항상 1페이지부터 시작한다. 데이터 오표시는 아니지만, 일시적 오류가 나면 같은 페이지를 바로 재시도할 수 없다.
- 결과 컨테이너에는 `aria-busy`가 있지만 결과 제목·빈 결과에 직접적인 live status가 없다. `#page-status`는 `role=status`지만 0건 첫 페이지에서 상위 페이지 영역이 숨겨진다. 오류는 `role=alert`다. 빈 결과 완료 알림을 보조기기가 알리는지는 실제 보조기기 검사가 남아 있다.

## 추가한 오프라인 검사

- `tests/ui_transactions_v03.cjs`: Node 기본 테스트 러너와 최소 DOM 대역으로 실제 `static/app.js`의 거래 화면 함수를 실행한다. **13개 통과**.
- `tests/test_review_ui_v03.py`: 위 검사를 pytest 전체 실행에 연결하는 래퍼. Node가 없는 환경에서는 명시적으로 건너뛴다.
- 실행: `node --test tests/ui_transactions_v03.cjs` 및 `.venv/bin/python -m pytest -q tests/test_review_ui_v03.py`.
- 브라우저 자동화·실제 네트워크·사용자 인증키를 사용하지 않았다. 이 검사는 화면 배치·실제 브라우저 이벤트 순서·실제 국토부 필드 계약 확인을 대신하지 않는다.

통합 담당자의 브라우저 확인에는 모드 전환, 입력란 포커스를 유지한 채 코드 편집, 0건·제외행·페이지 전환, 작은 화면의 표 스크롤을 포함하도록 전달했다.
