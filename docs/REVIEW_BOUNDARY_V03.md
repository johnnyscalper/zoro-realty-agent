# V03 — 무자료 응답과 검증 보고서의 경계 검토

검토일: 2026-11-12. 범위는 `app/molit.py`의 응답 해석과
`scripts/check_api.py`의 스키마 `1.1` 상태 판정이다. 이 검토에서는 외부
요청을 보내지 않았고 실제 인증키, `.env`, 사용자 업로드를 열지 않았다.
`app.main`의 기본 앱도 불러오지 않았다. 아래 결과는 합성 XML과 가짜 키를
사용한 오프라인 검증이며, 실제 인증 성공 여부는 별도 실조회 기록으로 판단한다.

## 추가로 발견하여 수정한 두 가지 문제

| 문제 | 수정 전 재현 결과 | 수정 |
|---|---|---|
| 무자료 헤더가 본문의 거래와 전체 건수를 버림 | `03 / NODATA_ERROR`인데 본문에 거래와 `totalCount=2`가 있으면 전체·반환·제외 건수를 모두 0으로 만들었다. 검증 보고서는 이를 `OK`로 받을 수 있었다. | 무자료 응답에도 본문이 있으면 거래 행과 전체 건수를 확인한다. 행이 있거나, 명시된 전체 건수가 0이 아니거나 유효한 정수가 아니면 `MOLIT_INVALID_RESPONSE`로 거절한다. |
| 게이트웨이의 두 메시지 중 하나만 검사 | `returnAuthMsg=NODATA_ERROR`가 있으면 `errMsg=SERVICE_KEY_IS_NOT_REGISTERED_ERROR`를 읽지 않아 인증 오류를 정상 0건으로 바꿀 수 있었다. | `returnAuthMsg`와 `errMsg`를 모두 오류 분류에 사용한다. 어느 필드에 있든 인식 가능한 인증·쿼터·시간 초과 오류가 무자료 처리보다 우선한다. |

본문이 없는 표준 `03` 응답, 오류 없는 `0 / NO_DATA` 응답, 본문의 전체
건수가 0이고 행이 없는 무자료 응답은 계속 정상 처리한다. 이 변경은 원본
메시지를 사용자 응답이나 보고서에 복사하지 않는다.

## 기존 수정과 함께 확인한 상태 판정

| 경계 | 확인 결과 |
|---|---|
| 명시적인 제공기관 오류 코드와 무자료 메시지 | 인증·쿼터·시간 초과·서비스 오류가 정상 0건으로 바뀌지 않는다. |
| 후속 페이지와 전체 건수 | 페이지 크기, 요청 페이지, 남은 위치를 넘는 행을 검사한다. 남은 위치가 있는데 비어 있는 페이지는 오류다. 전체 범위를 지난 빈 페이지는 전체 건수를 유지한다. |
| 일부 또는 모든 행의 변환 실패 | 제공기관 전체 건수를 유지하고 `skipped_count`로 제외 건수를 남긴다. 검증 보고서는 `PARTIAL`이며 `both_apis_verified=false`다. |
| 보고서의 조회 종류·지역·계약월 | 반환 메타데이터가 요청과 일치해야 한다. 유효한 요청의 조건만 `query`에 기록하고, 잘못된 인수는 보고서에 복사하지 않는다. |
| 한 API만 요청 | 선택하지 않은 서비스는 `NOT_REQUESTED`다. 요청한 API가 정상이어도 두 API 전체 상태는 `PARTIAL`, `both_apis_verified=false`다. 요청한 API가 정상이면 명령의 종료 코드는 0일 수 있다. |
| 두 API 모두 정상 | 두 서비스 상태가 모두 `OK`인 실행만 `VERIFIED / both_apis_verified=true`가 된다. 정상 0건에는 개별 거래 필드를 확인하지 못했다는 경고가 붙는다. |
| 실패한 두 API | `FAILED`, 안전한 오류 코드, `null` 건수를 저장한다. 두 API 정상 완료 안내를 출력하지 않는다. |
| `checked_at`과 provenance | `checked_at`은 실행되지 않은 항목에도 생기는 프로그램 시각이다. provenance는 요청 경로와 검증 범위다. 둘만으로 실제 요청·인증 성공을 증명하지 않는다. |

## 남겨 둔 내부 계약 의존성

보고서의 `_summarize_page()`는 종류·지역·계약월과 건수를 다시 검사하지만,
반환 사전의 `page_no`와 `num_of_rows`를 별도로 검사하지 않는다. 따라서 이
함수에 직접 다른 페이지 정보를 넣은 사전도 건수 조건을 충족하면 `OK`가
될 수 있다. 현재 실조회 경로의 `fetch_transactions()`는 일반 XML 응답에서
실제 페이지·페이지 크기와 요청의 일치를 검사하고, 무자료 응답의 메타데이터는
검증된 요청으로 구성한다. 보고서의 `query` 역시 요청 조건을 기록한다.

이번 수정은 실제 파서에서 재현된 두 모순에 한정했고, 이 중복 검사 보강은
하지 않았다. 추후 검증 보고서가 다른 fetcher나 외부 저장 응답을 입력으로
받는다면 페이지 정보도 보고서 경계에서 다시 검사해야 한다.

페이지 건수 검사는 반환 행이 허용 범위를 넘거나 필요한 페이지가 완전히
비어 있는 모순을 찾는다. 모든 페이지를 수집하거나 제공기관의 전체 건수를
독립적으로 대조하는 검사가 아니므로, 한 페이지의 `OK`를 전체 자료 완전성
확인으로 해석하면 안 된다.

새 `tests/test_boundary_v03.py`는 32개 사례다. 모순된 무자료 본문 12개,
정상 무자료 응답 6개, 두 게이트웨이 메시지 위치의 오류 우선순위 12개,
실제 HTTP 클라이언트·파서·보고서 경로를 오프라인 전송기로 연결한 2개
사례를 포함한다. 마지막 두 사례는 잘못된 무자료 입력으로 두 API 검증이
성공하거나 정상 완료 안내가 출력되지 않는 것까지 확인한다.

이 통과 결과는 인증 승인, 실응답의 항목별 명세, 현재 매물 상태 또는 Zoro
실행을 검증한 기록이 아니다.
